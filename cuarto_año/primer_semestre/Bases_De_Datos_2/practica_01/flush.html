El flush en Hibernate

Cuándo y cómo los cambios en memoria viajan a la base de datos

1 · Qué es (y qué NO es) — flush ≠ commit

🔄 FLUSH

Es el momento en que Hibernate sincroniza el contexto de persistencia con la base: traduce los cambios hechos en memoria a sentencias SQL (INSERT/UPDATE/DELETE) y las envía a la base.

▸ Manda el SQL, pero dentro de la transacción — todavía se puede hacer rollback.

✅ COMMIT

Es el cierre de la transacción: hace que todo lo enviado se vuelva permanente en la base. El commit dispara un flush antes de confirmar.

▸ Confirma definitivamente. Después del commit ya no hay vuelta atrás.

flush = "escribí el SQL ahora"  ·  commit = "hacelo permanente". Puede haber varios flush dentro de una transacción, pero un solo commit al final.

2 · El movimiento entre capas

🧠 Memoria — contexto de persistencia

Modificás objetos managed: service.setPrice(150). El cambio vive solo en RAM. No hay SQL todavía.

▼ FLUSH — dirty checking genera el SQL↓

📝 SQL generado

Hibernate compara cada entidad con su snapshot y arma las sentencias: UPDATE service SET price=150 WHERE id=5

▼ JDBC — envía las sentencias↓

🗄️ Base de datos (dentro de la transacción)

El SQL se ejecuta, pero el cambio aún no es permanente: vive dentro de la transacción abierta y podría revertirse con un rollback.

▼ COMMIT↓

🔒 Cambios permanentes

Al hacer commit, todo lo enviado por el flush queda confirmado en la base de forma definitiva.

3 · ¿Cuándo ocurre el flush? (FlushMode)

✅ Al hacer commit

El caso típico. Antes de confirmar la transacción, Hibernate hace flush automáticamente para que la base tenga todos los cambios. Es lo más común.

🔍 Antes de una query

Si vas a ejecutar una consulta (HQL) que podría verse afectada por cambios pendientes, Hibernate hace flush antes para que la consulta lea datos consistentes. (FlushMode.AUTO, el default)

✋ Manual

Podés forzarlo con session.flush(). Útil en procesos batch: hacer flush + clear cada N entidades para liberar memoria sin esperar al commit.

El comportamiento lo define el FlushMode: AUTO (default: commit + antes de queries afectadas), COMMIT (solo al commit), MANUAL (solo si llamás flush()).

4 · ¿Qué hace por dentro? (dirty checking)

1
Recorre las entidades managed

Toma cada entidad que está en el contexto de persistencia (caché L1).

2
Compara contra el snapshot

Para cada una, compara su estado actual con la "foto" que guardó al cargarla. Si difiere, la marca como dirty (sucia).

3
Genera el SQL en orden

Emite INSERT (entidades nuevas), UPDATE (las dirty) y DELETE (las removed), respetando dependencias de FK.

4
Envía las sentencias a la base

Vía JDBC (pudiendo agruparlas en batch). El contexto queda sincronizado con la base.

5 · Ejemplo paso a paso (actualizar precio + leer)

begin tx
session.beginTransaction() — se abre la unidad de trabajo.
leer
Service s = repo.findById(5); → MANAGED · Hibernate guarda el snapshot {price:100}.
modificar
s.setPrice(150); → cambia solo en memoria. No hay SQL todavía.
FLUSH
Antes del commit (o de una query afectada): dirty checking detecta 150 ≠ 100 → genera y envía UPDATE service SET price=150 WHERE id=5.
commit
tx.commit() → el UPDATE ya enviado se vuelve permanente. La sesión se cierra y s pasa a DETACHED.

Nunca se llamó a save() ni update(): el flush + dirty checking detectaron el cambio solos, porque s estaba managed.

La idea central: el flush es el puente que lleva los cambios que hiciste sobre objetos en memoria hacia la base de datos, traduciéndolos a SQL mediante dirty checking. No lo confundas con el commit: el flush manda el SQL (todavía reversible dentro de la transacción), el commit lo hace permanente. Por eso modificar una entidad managed "se guarda solo" — el flush, disparado al commit o antes de una query, se encarga de sincronizar sin que escribas un save().
