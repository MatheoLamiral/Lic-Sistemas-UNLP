DAOs y Repositorios

La capa de acceso a datos: qué son, dónde viven y en qué se diferencian

El DAO/Repositorio es la frontera: por encima se piensa en objetos; por debajo, en tablas y SQL. Aísla el resto de la app de la tecnología de persistencia.

2 · Los dos patrones

🔧 DAO (Data Access Object)

Orientado a la persistencia / tabla

Patrón que abstrae y encapsula el acceso a una fuente de datos. Responde "cómo guardar/recuperar". Suele haber un DAO por entidad/tabla, con operaciones CRUD.

public interface UserDAO {
  void save(User u);
  User findById(Long id);
  List<User> findAll();
  void update(User u);
  void delete(User u);
}
// impl usa Session / EntityManager
  • Piensa en términos de la tabla
  • API técnica: CRUD genérico
  • Una clase por entidad

📚 Repository (Repositorio, viene de DDD)

Orientado al dominio

Patrón que actúa como una colección en memoria de objetos del dominio. Responde "dame los objetos que cumplen X". Trabaja sobre raíces de agregado y habla el lenguaje del negocio.

@Repository
public interface UserRepository
        extends JpaRepository<User, Long> {

  Optional<User> findByUsername(String u);
  List<User> findByActiveTrue();
}
  • Piensa en términos del dominio
  • API expresiva (consultas con sentido de negocio)
  • Como una "colección" de entidades

3 · DAO vs Repository

CriterioDAORepository
OrigenPatrón clásico de acceso a datosDomain-Driven Design (DDD)
EnfoqueLa fuente de datos (tabla/persistencia)El dominio (colección de objetos)
Pregunta que responde"¿cómo persisto esta entidad?""¿qué objetos del dominio necesito?"
GranularidadUno por tabla/entidadUno por raíz de agregado
Estilo de APICRUD técnico (save, update…)Colección + consultas de negocio (findByUsername…)
En la prácticaLo escribís a mano sobre `Session`/`EntityManager`Spring Data lo genera (interfaz `JpaRepository`)

En la práctica los términos se solapan: ambos resuelven "aislar el acceso a datos". La diferencia es de énfasis (técnico vs dominio). Spring Data unificó el nombre en Repository.

4 · Flujo de una operación (comprar un tour)

1
Controller recibe POST /purchases

Llama al servicio. No toca la base.

2
Servicio @Transactional comprar(...)

Abre la transacción y coordina varios repositorios: routeRepository.findById(), userRepository.findById(), purchaseRepository.save().

3
Repositorio purchaseRepository.save(compra)

Expone la operación; por dentro delega en el ORM. La lógica de negocio no sabe cómo se guarda.

4
Hibernate traduce a SQL

Genera el INSERT, gestiona la Session atada a la transacción del servicio.

5
Base de datos ejecuta el SQL

Al hacer commit la compra queda persistida; las filas vuelven como objetos.

La idea central: el repositorio/DAO es la frontera que aísla al resto de la aplicación de cómo se guardan los datos. El servicio maneja la transacción y la lógica de negocio coordinando uno o varios repositorios; el repositorio expone operaciones sobre entidades; el ORM hace la traducción a SQL. Así, si mañana cambia la tecnología de persistencia, solo cambia la capa de repositorios — el resto de la app no se entera.
