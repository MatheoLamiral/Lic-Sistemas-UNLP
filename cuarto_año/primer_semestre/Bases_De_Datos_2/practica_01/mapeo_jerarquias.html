Mapeo de jerarquías de herencia

Cómo representar User → DriverUser / TourGuideUser en tablas relacionales

0 · El problema y la jerarquía de ejemploEl modelo relacional NO soporta herencia → JPA ofrece 3 estrategias para "aplanarla"

User

id · username · name

DriverUser

+ expedient

TourGuideUser

+ education

Se configura con @Inheritance(strategy = InheritanceType.XXX) sobre la clase raíz User.

1 · SINGLE_TABLE una sola tabla para toda la jerarquía + columna discriminadora · (es la estrategia por defecto)

☕ Java
@Entity
@Inheritance(strategy =
   InheritanceType.SINGLE_TABLE)
@DiscriminatorColumn(name="user_type")
class User { Long id; String name; }

@Entity
@DiscriminatorValue("DRIVER")
class DriverUser extends User {
  String expedient;
}

@Entity
@DiscriminatorValue("GUIDE")
class TourGuideUser extends User {
  String education;
}

La columna user_type (discriminadora) dice de qué clase es cada fila. Cada fila tiene NULL en las columnas que no le corresponden.

Ventajas

  • La más rápida (sin JOINs)
  • Consultas polimórficas triviales
  • Simple, una sola tabla

Desventajas

  • Muchos NULLs (espacio desperdiciado)
  • Tabla ancha y dispersa
⛔ Restricción clave: las columnas de las subclases deben ser NULLABLE. No podés poner NOT NULL en expedient ni education, porque las filas de la otra subclase las tendrán vacías. (La validación de obligatoriedad queda en la app, no en el esquema.)
✅ Conviene cuando: priorizás rendimiento y hacés muchas consultas polimórficas (es la más eficiente para consultar toda la jerarquía junta), y las subclases agregan pocos campos propios. Es la opción por defecto.
↳ Si necesitás mantener restricciones (NOT NULL, etc.) sobre los hijos, usá JOINED en su lugar.

2 · TABLE_PER_CLASS una tabla por clase concreta, con TODAS las columnas (las comunes se repiten)

☕ Java
@Entity
@Inheritance(strategy =
   InheritanceType.TABLE_PER_CLASS)
class User { Long id; String name; }

@Entity
class DriverUser extends User {
  String expedient;
}

@Entity
class TourGuideUser extends User {
  String education;
}
// sin discriminador
🗄️ Tablas resultantes (una por clase concreta)

Las columnas comunes (id, name) se repiten en cada tabla. No hay tabla para User ni discriminador.

Ventajas

  • Sin NULLs (cada tabla es limpia)
  • Cada clase concreta = su tabla
  • Sin columna discriminadora

Desventajas

  • Columnas comunes duplicadas
  • Consulta polimórfica = UNION de todas las tablas (lenta)
  • Cambiar un campo común toca todas las tablas
⛔ Restricción clave: no se puede usar GenerationType.IDENTITY para el id. Como los ids deben ser únicos en toda la jerarquía (para las consultas polimórficas con UNION), un autoincremental por tabla chocaría. Hay que usar SEQUENCE o TABLE.
✅ Conviene cuando: hacés muchas consultas sobre los hijos por separado y no te interesan las polimórficas (que acá serían un UNION lento). Tablas limpias sin NULLs. En la práctica es la menos usada.

3 · JOINED una tabla por clase, pero normalizada: la base tiene lo común, las hijas solo lo propio + FK al padre

☕ Java
@Entity
@Inheritance(strategy =
   InheritanceType.JOINED)
class User { Long id; String name; }

@Entity
class DriverUser extends User {
  String expedient;   // puede ser NOT NULL
}

@Entity
class TourGuideUser extends User {
  String education;
}

El id de cada tabla hija es a la vez PK y FK hacia user.id. Para leer un DriverUser completo se hace JOIN entre user y driver_user.

Ventajas

  • Normalizado: sin NULLs ni duplicación
  • Permite NOT NULL en campos de subclase
  • Esquema limpio y prolijo

Desventajas

  • Leer una subclase requiere JOIN
  • Insertar toca 2 tablas
  • Consultas polimórficas = varios JOINs (más lento que SINGLE_TABLE)
ℹ️ Sin restricción dura como las otras, pero el costo es el rendimiento: cada lectura/inserción de una subclase implica unir o tocar la tabla padre y la hija.
✅ Conviene cuando: necesitás mantener restricciones fuertes en todo el esquema (NOT NULL y constraints tanto en el padre como en los hijos) y un modelo normalizado, aun a costa de los JOINs. Ideal si las subclases tienen muchos campos propios.

Cómo elegir, en una línea cada una: SINGLE_TABLE → rapidez y simplicidad, aceptando NULLs y sin poder exigir NOT NULL en subclases (el default). TABLE_PER_CLASS → tablas limpias e independientes, pero pagás duplicación, UNIONs y perdés IDENTITY. JOINED → el más normalizado y prolijo (permite NOT NULL), a costa de JOINs en cada acceso.

En tu TP la jerarquía User usa SINGLE_TABLE: pocas columnas extra (expedient, education), prioriza rendimiento, y la columna discriminadora user_type distingue cada tipo.
