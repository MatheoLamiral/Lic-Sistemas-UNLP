De JDBC a Spring Data — el mismo ejemplo, 4 veces

Cómo encoge el código a medida que subimos de capa de abstracción

🎯 La misma tarea en los 4 enfoques
Buscar el usuario cuyo username es "ana" y devolverlo como objeto User.

1 · JDBC pelado — vos hacés TODO a mano

API de bajo nivel

JDBC

Conexión + SQL + mapeo manual + manejo de excepciones, todo explícito. boilerplate 
public User findByUsername(String username) {
  String sql = "SELECT * FROM app_user WHERE username = ?";
  try (Connection con = dataSource.getConnection();           // 1. conexión
       PreparedStatement ps = con.prepareStatement(sql)) {     // 2. statement
    ps.setString(1, username);
    try (ResultSet rs = ps.executeQuery()) {                   // 3. ejecutar
      if (rs.next()) {
        User u = new User();                                 // 4. mapeo MANUAL
        u.setId(rs.getLong("id"));                            //    columna → atributo
        u.setUsername(rs.getString("username"));
        u.setName(rs.getString("name"));
        u.setEmail(rs.getString("email"));
        return u;
      }
      return null;
    }
  } catch (SQLException e) { throw new RuntimeException(e); }   // 5. errores
}
▸ ~18 líneas. Vos manejás conexión, SQL crudo, recorrido del ResultSet, mapeo columna→atributo a mano y excepciones. Atado al SQL del motor.

2 · Hibernate nativo — el ORM mapea y genera el SQL

Implementación ORM

Hibernate (Session + HQL)

Consultás objetos con HQL; el mapeo y la conexión los hace el ORM. boilerplate 
public User findByUsername(String username) {
  return sessionFactory.getCurrentSession()
      .createQuery("from User u where u.username = :u", User.class)  // HQL (objetos)
      .setParameter("u", username)
      .uniqueResult();                                            // mapeo automático
}
▸ ~5 líneas. No hay conexión ni ResultSet ni mapeo manual: HQL habla de objetos (User.username) y Hibernate genera el SQL y arma el User. API propia de Hibernate.

3 · JPA — lo mismo, pero con la API estándar

Especificación estándar

JPA (EntityManager + JPQL)

Igual que Hibernate, pero con interfaces estándar (portable a otros proveedores). boilerplate 
public User findByUsername(String username) {
  return entityManager
      .createQuery("select u from User u where u.username = :u", User.class) // JPQL
      .setParameter("u", username)
      .getSingleResult();
}
▸ ~5 líneas. Prácticamente idéntico a Hibernate, pero usa EntityManager y JPQL (el estándar). Por debajo lo ejecuta Hibernate igual — la diferencia es que el código no depende de Hibernate.

4 · Spring Data JPA — ni siquiera escribís la consulta

Abstracción máxima

Spring Data (Repository)

Declarás el método en una interfaz; Spring genera la implementación (proxy). boilerplate 
public interface UserRepository extends JpaRepository<User, Long> {

  Optional<User> findByUsername(String username);   // ¡solo la firma!
}
// no escribís el cuerpo: Spring deriva la consulta del nombre del método
▸ 1 línea (una firma). No hay implementación: el proxy dinámico parsea findByUsername y arma la JPQL solo. Por debajo: JPA → Hibernate → JDBC → SQL.

La evolución en una idea: es la misma tarea resuelta a niveles crecientes de abstracción. JDBC te hace escribir SQL crudo y mapear a mano. Hibernate mapea objeto⇄tabla y genera el SQL (vos solo pedís en HQL). JPA es lo mismo pero con una API estándar (Hibernate por debajo). Spring Data da el último salto: ni escribís la consulta — declarás la interfaz y un proxy la implementa. Cada nivel se apoya en el anterior: arriba escribís menos, pero abajo siempre termina ejecutándose JDBC contra la base.
