Spring Data JPA — proxies dinámicos

Cómo se implementa un repositorio en tiempo de ejecución sin que escribas la implementación

1 · Vos escribís una interfaz… ¿quién la implementa?

✍️ Lo que vos escribís
@Repository
public interface UserRepository
    extends JpaRepository<User, Long> {

  Optional<User> findByUsername(String u);
}
// ¡es una INTERFAZ! no hay clase
// que la implemente en tu código
→en el arranque
Spring genera
⚙️ Lo que corre en runtime
// Spring crea en memoria una clase
// que NO existe en tu código fuente:
$Proxy$UserRepository
   implements UserRepository

// es un PROXY DINÁMICO que intercepta
// cada llamada a tus métodos y la enruta

Nunca escribís una clase UserRepositoryImpl. Spring Data fabrica la implementación sola, en tiempo de arranque, como un proxy dinámico.

2 · Cómo se fabrica el proxy (en el arranque)

1 · Escaneo de repositorios

Al iniciar, Spring detecta todas las interfaces que extienden Repository/JpaRepository.

↓ por cada interfaz, la RepositoryFactory …

2 · Crea un proxy dinámico

Usa java.lang.reflect.Proxy (proxy JDK) para generar, en memoria, un objeto que implementa la interfaz. Le asocia un InvocationHandler que interceptará las llamadas.

↓

3 · Registra el proxy como bean

Ese proxy se mete en el contenedor de Spring. Cuando hacés @Autowired UserRepository, te inyectan el proxy (no una clase tuya).

3 · Qué pasa al llamar un método (en runtime)

🧩 Tu servicio

userRepository.findByUsername("ana")

↓ la llamada NO va a una clase tuya, va al…

🎭 Proxy dinámico

Intercepta la llamada y se la pasa a su InvocationHandler (el "cerebro" que decide qué hacer con cada método).

↓ el handler clasifica el método (ver sección 4)

🔧 Ejecución

Según el tipo de método, delega en SimpleJpaRepository o arma y ejecuta una consulta a través del EntityManager (que por debajo es Hibernate).

↓

🗄️ Hibernate → SQL → Base de datos

El EntityManager traduce a SQL, ejecuta y devuelve el resultado mapeado a entidades, que sube de vuelta por la misma cadena.

4 · Las tres rutas que decide el handler

① Método CRUD heredado

save() · findById() · delete()

Viene de JpaRepository. El handler delega en la implementación por defecto SimpleJpaRepository, que usa el EntityManager.

② Query derivada del nombre

findByUsername(...)

El handler parsea el nombre del método (con un PartTree) y construye la JPQL automáticamente. Ver sección 5.

③ Método con @Query

@Query("select u …")

Si el método tiene @Query, el handler ejecuta esa consulta directamente, sin parsear el nombre.

5 · Ejemplo: cómo se deriva una query del nombre

findByUsernameAndActiveTrue(String u)
find … By→SELECT u FROM User u WHERE
Username→u.username = ?1 (toma el 1er parámetro)
And→AND
ActiveTrue→u.active = true
SELECT u FROM User u WHERE u.username = ?1 AND u.active = true

El PartTree tokeniza el nombre del método en palabras clave (find, By, And, True, OrderBy…) y propiedades de la entidad (Username, Active), y arma la JPQL. Por eso los nombres deben coincidir con los atributos de la entidad — si escribís findByUserName y el campo es username, falla al arrancar.

La idea central: en Spring Data no implementás el repositorio — declarás una interfaz y, en el arranque, Spring fabrica un proxy dinámico que la implementa. Ese proxy intercepta cada llamada con un InvocationHandler que la clasifica en tres rutas: CRUD heredado (→ SimpleJpaRepository), query derivada del nombre (→ parsea y arma la JPQL) o @Query (→ ejecuta la consulta dada). Todo termina pasando por el EntityManager (Hibernate) → SQL. Por eso "escribís menos": el código que en el TP1 escribías a mano (la Session, el HQL del CRUD) ahora lo genera el proxy.
